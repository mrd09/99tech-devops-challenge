# Problem 3 — runtime evidence

## Scope and baseline

Commands were executed against the isolated Compose project `challenge-p3-review`, using the supplied files in `src/problem3`. The supplied baseline is recorded in git at `d7384f8`. Its NGINX upstream already targets `api:3000`.

The normal startup command from this directory is:

```sh
docker compose -f docker-compose.yml up --build -d
```

The actual review command added a project name to isolate these containers:

```sh
docker compose -f docker-compose.yml -p challenge-p3-review up --build -d
```

All four services started. A direct curl through port 8080 returned `200` with `ok: true` from `/api/users`. This handler executes `SELECT NOW()` and an awaited Redis `SET`; it does not query user records.

## Controlled SQL-error probe

A separate Node script inside the baseline API container created its **own** pool with `max: 2` and a 150-ms acquisition timeout. It repeated the original sequence:

```js
const client = await pool.connect();
await client.query("SELECT 1/0"); // intentional error, not the API's query
client.release();
```

Two query errors bypassed release; the third acquisition timed out. The probe then released its held clients and closed that pool. A second independent pool used `pool.query()` for three injected errors followed by `SELECT 1`:

```text
{"probe":"original-release-pattern","injectedSQL":"SELECT 1/0","results":[{"attempt":1,"error":"22012"},{"attempt":2,"error":"22012"},{"attempt":3,"error":"timeout exceeded when trying to connect"}],"checkedOut":2}
{"probe":"pool-query-pattern","injectedFailures":3,"recoveryQuery":"ok","checkedOut":0}
```

This demonstrates the failure of the **release pattern** with a real database. It does not demonstrate that the healthy `/api/users` timestamp query failed in normal traffic or caused the reported incident. Both probe pools were cleaned up, with no application data modified.

## Remaining limitations

- The original intermittent user report remains unassigned. Obtain the exact workflow/client trace and correlate it with retained endpoint evidence.
- Fault injections demonstrate conditional failure paths; they are not spontaneous reproduction of that report.
- Host networking/descriptor capacity, long-duration leaks, stalled network packets, production dataset, traffic distribution, backups and multi-instance failover were not comprehensively tested.
- Docker health flags do not automatically restart unhealthy containers or remove NGINX targets. Runtime deadlines/reconnection handle dependency interruptions here.
- The original `max_connections=20` SQL file remains unmounted. The timestamp endpoint needs no custom schema, and applying that sample cap without a pool/capacity budget would change behavior. The measured baseline limit was 100.
- Existing anonymous-volume data is not automatically copied into the new named volume. Migrate/restore before making that change in a real environment.
